# 漏洞扫描报告

## 整体结论

经多源合议，确认存在一个通过 Redis 缓存投毒（Cache Poisoning）触发 Flask-Caching Pickle 反序列化，最终导致远程代码执行（RCE）的高危漏洞链。攻击者可以利用笔记接口对 `title` 参数缺乏过滤的缺陷，直接向 Redis 写入任意键值对。通过构造特定的缓存键名并注入带有 `!` 前缀的恶意 pickle payload，可以覆盖合法缓存，并在后续读取该缓存时触发反序列化执行任意命令，从而完全控制服务器并窃取敏感文件（如 /flag.txt）。

## [HIGH] Redis 缓存投毒导致 Flask-Caching 反序列化 RCE
- 文件: app.py
- 行号: 24
- 代码: `title = request.form.get('title', default=None)\n...\nredis.setex(name=title, value=content, time=3)`
- 攻击路径: 攻击者可以利用 `app.py` 中 `title` 参数未经过任何过滤直接作为 Redis Key 写入的缺陷（H2），结合 Flask-Caching 库会将以 `!` 开头的缓存值进行 pickle 反序列化的特性（H1），实现缓存投毒。具体路径为：攻击者构造一个特定的缓存键（例如 `flask_cache_view//test1`）作为 `title` 参数，并将一个经过精心设计的恶意 pickle payload（以 `!` 开头）作为 `content` 上传。由于程序直接调用 `redis.setex` 写入，攻击者成功在 Redis 中覆盖了合法的缓存项。当系统后续读取该缓存键时，Flask-Caching 会触发反序列化，导致攻击者预设的恶意代码（如 `os.system`）在服务器上执行，最终实现 RCE。
- 修复: 1) 对 `title` 参数进行严格的输入验证，限制其仅允许字母、数字和下划线，防止任意 Redis 键注入；2) 在 Flask-Caching 的配置中禁用 pickle 序列化，改用更安全的序列化方式；3) 增加对用户上传内容长度和类型的校验。

## 攻击链推演（Deepen）

### 攻击链 1
- 前置条件:
  - 攻击者能够控制Redis缓存中的特定键名，例如通过构造特定的标题名称来注入恶意缓存键。
  - 攻击者可以构造并上传一个经过精心设计的pickle序列化对象，该对象能够在Flask-Caching反序列化时执行任意代码。
- 横向移动/影响面:
  - 攻击者可以利用反序列化漏洞执行任意代码，例如读取服务器上的敏感文件（如flag.txt）。
  - 攻击者可以进一步将恶意代码扩展到其他系统服务，例如通过curl命令将flag内容发送到攻击者的服务器。
- 最终影响: 攻击者能够通过反序列化漏洞执行任意代码，从而完全控制服务器，窃取敏感数据或破坏系统。
- 修复建议: 修复措施包括：1) 在Flask-Caching配置中禁用pickle序列化，使用更安全的缓存存储方式；2) 限制Redis缓存键的命名规则，防止恶意缓存键注入；3) 对用户输入进行严格的验证和过滤，防止不受信任的数据被存储到缓存中。

### 攻击链 2
- 前置条件:
  - 攻击者能够向 Redis 提交任意键值对
  - Redis 中存储的缓存值会被 Flask-Caching 读取并反序列化
- 横向移动/影响面:
  - 攻击者构造恶意标题和内容，覆盖特定缓存键
  - 触发缓存读取时，恶意 pickle 数据被反序列化，执行任意代码
- 最终影响: 攻击者能够远程执行代码，读取 /flag.txt 文件内容并外传
- 修复建议: 修改 app.py 中的标题过滤逻辑，限制 title 参数只能包含字母数字下划线，防止缓存键覆盖
