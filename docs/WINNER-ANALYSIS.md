> 获奖项目共 14 个，本篇深度分析 5 个核心赛道项目（AegisFlow / Chancery / Signet / DealForge / Time-Out）+ 速览 6 个应用型项目（PantryProof / AccessForm / DepositCheck / compare.ai / LaunchKit / Unmet）

## 核心结论（先说重点）

**这批赢家的核心赛道高度一致：「AI Agent 的信任 / 授权 / 防滥用 / 人类责任」。** 这与 CodeRisk Arcanum（检测 AI 时代漏洞 + 提示注入防护）**完全同赛道**。但赢家们把"AI Agent 安全"做成了**可验证、可测试、可追溯的工程机制**，而不是停留在"加个确认按钮"或"prompt 约束"。

> **最深刻的教训：真正的 AI Agent 安全，靠的不是 prompt 约束，而是「不可逆操作锁定 + 多源验证 + 诚实可追溯日志」这三件可测试的工程机制。**

## 项目 1：AegisFlow（总冠军）

### 定位
> **"AI 做全部调研，然后停手。批准、拒绝、签字永远不是 agent 的权限。"**
> 反"全自动代理"潮流，主打"AI 辅助 + 人类最终决策"的安全边界。

### 核心设计哲学

**① "Human keeps the pen"（人类拿笔）**
- AI 跑完整个调查（读文档、搜网页、查域名、交叉验证、打分）→ **然后停止**
- Approve / Reject / Sign 三个动作，**由有限状态机（FSM）+ 命名守卫（named guard）强制锁定给人类**，不靠 prompt 约束
- 关键洞察：**不靠提示词"劝"AI 别越权，而是用代码结构"物理上禁止"AI 越权**

**② 多源交叉验证（4 个独立系统对同一供应商）**
```
某供应商声称"2018 年成立"
├─ 商业注册（Nutrient DWS）→ 实际 FORMED: 2021-06-08 ✗
├─ ISO9001 证书（Nutrient）→ 注册机构无资质 ✗
├─ 实时网络（SerpApi）→ 几乎没有独立佐证 ✗
└─ 域名系统（name.com）→ 该域名无人注册、仍在出售 ✗
```
- 一个供应商可以伪造 PDF，但**让 4 个独立来源一致认同就难得多**。

**③ 计算出的结论，不是脚本写死的（verdicts are computed, not scripted）**
- 验证规则按文档类型匹配后读取字段，**不引用文件名**
- 测试：同一份代码、改字段值 → 不同判定
- 避免"写死某份文档是问题文档"的作弊式硬编码

**④ 权重无法淹没诚实（integrity cap）**
- 风险模型完全透明、可实时调节
- 即使把"成本权重"拉到最大，**带未解决证据冲突的供应商仍被封顶在 49/100**
- 设计亮点：给"诚信门槛"设硬上限，权重调不动它

**⑤ 工具分级 + 不可逆动作锁定（agent-tools.ts）**
- 每个文档操作注册风险等级（可逆 / 不可逆）
- esign.createFolder 是唯一不可逆操作：**仅限 HUMAN，且只能从唯一一个状态触发**
- 测试枚举每个 actor × 每个工作流状态，断言没有任何非人类组合能触达它

**⑥ 诚实的日志（Integration Activity Ledger）**
- 每次 sponsor API 调用进公开账本，标注 LIVE / LOCAL / DEMO SEEDED
- 配置表写 CONFIGURED 而不写 LIVE——"有 key"不等于"调用成功"
- 全流程零 key 跑通，靠诚实回退（honest fallback）

### 技术栈
doctavian / finite-state-machine / foxit-esign / google-gemini / name.com / next.js / node.js / nutrient-dws / playwright / react / serpapi / server-sent-events

### 💡 对 CodeRisk 可借鉴点

| AegisFlow 做法 | CodeRisk 可借鉴 |
|---------------|----------------|
| FSM + 守卫锁定高危操作给人类 | 报告发布 / 删除漏洞做成 HUMAN-only |
| 多源交叉验证（4 独立系统） | Agent C 的"三重交叉"升级为"多源合议" |
| 计算结论而非写死（规则读字段不读文件名） | PITAX 已对齐，加强"不引用文件名" |
| 工具分级 + 可逆/不可逆矩阵 | Agent 工具分级用"可逆性"而非"按功能枚举" |

## 项目 2：Chancery（Foxit 挑战冠军）

### 定位
> **"AI 代理的授权委托书（Power of Attorney）—— 人类签一份声明，标明 agent 可以承诺哪些不可逆行为；此后每个不可逆动作都对照这份签署文件核验，违规就大声拒绝并说明违反了哪一条。"**

### 解决的核心问题（比 AegisFlow 更深一层）

**痛点：** 现有 guardrail（配置文件、策略 YAML、prompt 白名单）都有**致命缺陷——"承担后果的人从来没读过它们"**。人类在聊天窗口批准了摘要，但实际被执行的却是数据库里另一份完全不同的策略文件，任何有写权限的人都能偷偷放宽。

**Chancery 的答案：把"人类读的、签的"和"机器执行的"变成同一件事。** 消除"批准的东西"和"执行的东西"之间的差距。

### 核心机制

**① 人类签署"令状"（Writ）**
- 一份文档，精确说明 agent 可执行的不可逆行为：支出上限、白名单、名称模式、有效期、管辖权、升级阈值
- 签署后读回机器可执行的条款，每条带引用来源
- 亮点：**"未落地"视为"无权限"（grounded or absent, not permissive）**——只认能追溯来源的授权

**② 授权写进 DNS（WRIT1 TXT 记录）**
- 文档哈希 + agent 密钥 + 有效期 → 存进 DNS 的 TXT 记录（与 SPF/DKIM/CAA 同处）
- 每次不可逆动作：**重新解析 DNS → 重查文档哈希 → 重跑尽调 → 返回 ALLOW/DENY 并引用条款和页码**

**③ 撤销用"墓碑"而非删除**
- 删除记录会让仍从缓存取旧答案的解析器"看不到"已撤销 → 发布 tombstone 而非删除

**④ 边界画在"不可逆性"上（画一次）**
- 对比 Foxit 按"工具类别"画线（每新增能力就要单独排除，且不说明人类授权了啥）
- Chancery 改画在**不可逆性**：可逆的 → agent 自由调用；不可逆的 → 过一个统一闸门。agent 可请求任何事，答案永远是一句引用条款的裁决，而非"缺少能力"

**⑤ 证伪精神（诚实的技术主张）**
- 曾主张"PDF Services key 不等于 eSign 权限"，实测发现是**错的**（同一凭据能验证 eSign）
- 没有掩盖，而是**记录为 DISPROVED**，并补 3 个测试锁定真实响应
- 结论：**边界不能外包给供应商的 key 权限范围，必须是结构性的**——agent 进程从构造上就不持有 Foxit 凭据

### 工程严谨度（可验证的证明）

| 验证方式 | 内容 |
|---------|------|
| `pnpm bench` | 35 场景，预期判定+理由码运行前写死，35/35，零误放行、零误拒绝 |
| `pnpm verify` | 从公开 DNS 解析实时 writ；离线重演已发布判定，篡改结果会拒绝并退出非零 |
| `pnpm boundary` | 让 Foxit 真的拒绝我们，打印它说了什么 |
| `dig` 验证 | 域名 TXT 记录哈希 = 文档哈希，可从公开 DNS 独立核验 |
| 测试数 | 817 tests，tsc clean |

### 实现哲学（对重构极有价值）

> **决策引擎是输入的一个纯函数（无时钟、无网络、无数据库读）**——这正是 35 场景 benchmark 能存在、任何已发布判定能离线从证据包重演的原因。围绕它七个外部服务各一个端口，让"哪个供应商在哪个步骤承重"一目了然。

## 两项目共性提炼（可迁移到 AWS 参赛的核心设计模式）

1. **人类责任 = 可测试的工程机制，不是 UI 确认按钮**
   - FSM + 守卫锁定不可逆操作
   - "人类签的 = 机器执行的"消除鸿沟
   - 工具分级（可逆/不可逆）+ 可测试的 actor×state 矩阵

2. **多源交叉验证 = 对抗伪造的关键**
   - 单一来源可伪造，多独立来源一致才可信
   - 决策是"计算"出来的，不是"写死"的
   - 权重调不动诚信门槛

3. **诚实可追溯 = 信任的基础**
   - 公开账本、LIVE/LOCAL/DEMO 标注
   - 证伪记录（DISPROVED），不掩盖错误
   - 未落地视为无权限

4. **可验证性 = 最强的说服力**
   - 纯函数决策引擎 + 证据包可离线重演
   - 大量自动化测试（35/817）
   - 公开 DNS 哈希可独立核验

## 对 CodeRisk + AWS 参赛的落地建议

CodeRisk 已有基础：Agent C（三重交叉验证）+ PITAX（证据溯源）+ 报告（可追溯）。本次重构应重点强化：

1. **Agent 工具分级**：用"可逆/不可逆"定义工具权限，不可逆操作锁定给人类（借鉴 AegisFlow agent-tools.ts）
2. **Agent C 升级"多源合议"**：不只三重交叉，引入多独立来源一致性判定（借鉴 AegisFlow 4 系统）
3. **证据可追溯落地**：每条 PITAX 结论强制绑定证据行 + 来源（借鉴 Chancery grounded or absent）
4. **证伪记录机制**：Agent C 验证失败记录 DISPROVED，不默默忽略（借鉴 Chancery CLAIMS.md）
5. **可验证演示**：准备"改一条证据 → 判定翻转"的 live 演示，证明结论是算出来的不是写死的（借鉴两者）

## 项目 3：Signet（SerpApi / Nutrient 挑战获奖）

### 定位
> **"发票诈骗之所以得逞，是因为纸张无法证明谁发的。Signet 让发件人在自己域名的 DNS 上发布公钥，收款字段被签名覆盖，任何人都能用 dig 和 openssl 验证——无需账号、无需安装任何东西。"**

### 解决的痛点
- 2025 年发票篡改损失 30.5 亿美元，平均每起 12.2 万美元，86% 通过电汇/ACH 转走（FBI）
- 传统"打电话核实"不规模化、截止压力下被跳过、接电话者可能就是被黑的
- 传统"看外观"防伪失效：2026 年 5 月费用平台标记的假收据 71% 是机器生成的（一年前 0%）
- **Signet 换问题：不问"看起来真吗"，问"发件人说了他们发了这个吗"**

### 核心机制

**① DNS 发布公钥（信任锚）**
```
dig +short TXT _signet.northpost.dev
"v=SIGNET1; k=ed25519; p=Kqf0GFh29fslh099Tr9ruRvy6qI7ITeKC5KY8Wt0YWI="
```
- 由控制该域名的人发布，无 CA、无中间商、无我们的账号

**② 签名覆盖"决定钱去哪"的字段**
- 对收款字段签名：账号、金额、币种、银行代码、发票号
- 接收方用发件人自己域名的公钥验证

**③ 签名块 = 二维码（The mark）**

### 七重检查（各独立回答一个问题 + 独立证据）
signature / identity / lookalike / domain_age / fidelity / counterparty / duplicate

### 最精彩案例：密码学全对，仍是伪造
> 真实域名、真实密钥、真实签名，每个密码学步骤通过，但名字是伪造的——签名本身看不出这个。
```
pass signature      由 north-post.dev 签发
fail identity       自称 Maersk，但 north-post.dev 是 North Post Holdings
unknown lookalike   Maersk 无注册域名可比
unknown domain_age  注册 12 天，够新值得警惕
pass fidelity       页面与签名一致
fail counterparty   公开网络显示 Maersk 是 maersk.com
pass duplicate      之前没见过
VERDICT: FLAGGED
```
- **counterparty 是唯一能指出"真正域名"的检查**，靠 SerpApi 实时查询
- 区分了"拒绝文档"和"告诉别人发票本该来自哪"——后者价值大得多

### 关键设计决策
1. **判定是纯函数**：`decide(signals)` 无模型、无时钟、无网络、无状态。相同输入→相同输出。黄金测试套件而非置信分数——"不能重放的证据不是证据"
2. **查不到 = unknown，绝不 pass**：服务宕机时降低判定而非发明一个——故障恰恰是发伪造件的最佳时机
3. **唯一不可逆动作 = 发布 key 到 DNS**，任何 agent 无法触达，只有 broker 能发且须在读完会签文档后
4. **端口和适配器 + lint 规则**：域不导入供应商，测试用 fakes 无凭据跑通

### 信任阈值设计（人机协作边界）
- Nutrient 返回置信度 + 边界框（bounding box），界面把读到的值画在文档上
- 置信度驱动 0.80 阈值：低于它不做比较，字段转给人
- **判定函数永远看不到置信分数**——只看到 pass / fail / needs a person
- 人工决定记录在审计日志（谁做的、给他们看了什么）

### 💡 对 CodeRisk 可借鉴点
| Signet 做法 | CodeRisk 可借鉴 |
|------------|----------------|
| DNS 发布公钥做信任锚 | 漏洞报告加"发布者签名"验证真实性 |
| 签名覆盖关键字段而非整页 | PITAX 发现签名"关键证据字段" |
| 七重检查各带独立证据 + 纯函数判定 | Agent C 升级"多检查合议，每项独立证据" |
| 查不到 = unknown 绝不 pass | Agent C 遇"无法验证"标 UNKNOWN 而非放行 |

## 项目 4：DealForge（Doctavian 挑战获奖）

### 定位
> **"AI 解释，DealForge 确立商业真相，人类授权后果行为，Doctavian 生成并签名。这种分离就是产品本身。"**

### 解决的核心问题
商业协议始于混乱信息（销售笔记/定价碎片/折扣/条款），AI 能提取"看似合理"的事实，但**"看似合理"不等于"权威"。AI 如何在理解混乱交易时，不悄悄变成协议本身的真相来源？**

### 核心设计：三权分离（最精彩）
| 信息层 | 谁负责 | 性质 |
|--------|--------|------|
| AI Evidence | Gemini/Vertex AI | 候选事实 + 置信度 + 来源 + 歧义性 |
| Authoritative Deal State | DealForge 应用 | 产品身份、规范数据、就绪策略、确定性财务计算 |
| External Execution | Doctavian | 文档生成 + 签名 |

**AI 提取结果是"证据"，不是"权威业务状态"。** 模型不被允许：发明内部产品身份 / 计算权威合计 / 决定就绪性 / 发送外部签名请求 / 声明提供商完成。

### 核心机制
1. **权威货币用整数最小单位计算（LLM 不算钱）**
   - DealForge 计算：小计 EUR 118,560.00 / 折扣 EUR 14,227.20 / 最终值 EUR 104,332.80
   - **钱的计算是确定性的、由代码算的，绝不让 LLM 算钱**

2. **Draft ≠ Send（草案≠发送）**
   - 先建签名信封为 Draft，显示 `EMAIL SENT: NO`
   - 发送是后果性外部动作，需显式人类授权

3. **HMAC 密封工作流令牌（防篡改状态）**
   - 跨变更用 HMAC 密封令牌传递可信状态
   - 关键动作前重开验证可信状态，而非接受浏览器返回的权威数据

4. **Trusted Execution Trace（可信执行追踪）**
   - 记录可观察事件（提取/来源锚定/货币计算/生成/人类授权/签名/对账/工件检索）
   - 表示"操作证据"而非"隐藏的模型推理"

### 完整可信路径（最自豪成就）
> 混乱商业输入 → AI 提取 → 来源 → 确定性商业真相 → READY → 真实 Doctavian 生成 → 签名 Draft → **显式人类授权** → 真实签名 → 自动对账 → COMPLETED → 数字签名 PDF
- **最终演示到达真实已签名工件，而非模拟成功界面**——评委要"真做出来"不是"演示脚本"

### 最重要一课（刻进 DNA）
> **负责任的 AI 工作流，往往与其说是让模型更聪明，不如说是"设计好权威"。**
> - 模型可以解释信息，但不被允许让它成为权威
> - 提供商可以执行外部动作，但不拥有商业真相
> - 人类可以授权后果边界，而无需手动执行整个工作流

### 💡 对 CodeRisk 可借鉴点
| DealForge 做法 | CodeRisk 可借鉴 |
|---------------|----------------|
| 三权分离（AI证据/权威状态/外部执行） | Agent A 输出证据，Agent C 确立权威判定，人类授权处置 |
| 权威计算确定性（LLM 不算权威数值） | 严重级/风险评分由代码确定性计算，LLM 只给理由 |
| Draft ≠ Send（显式人类授权） | 报告"生成"与"发布/发送"分离，发布需人类授权 |
| HMAC 密封工作流令牌防篡改 | 跨 Agent 状态传递加防篡改校验 |

### 五个可迁移到 CodeRisk + AWS 参赛的核心设计原则

1. **人类责任 = 可测试的工程机制，不是 UI 确认按钮**
   - FSM + 守卫锁定不可逆操作（AegisFlow）
   - "人类签的 = 机器执行的"消除批准与执行鸿沟（Chancery）
   - 工具分级（可逆/不可逆）+ 可测试的 actor×state 矩阵

2. **权威的确定性分层（LLM 不掌握权威）**
   - 三权分离：AI 证据 / 权威状态 / 外部执行（DealForge）
   - 钱、严重级、风险评分等权威数值由代码确定性计算，LLM 只给理由和置信
   - 决策引擎是纯函数，无时钟无网络无状态（Signet/Chancery）

3. **多源交叉验证 = 对抗伪造的关键**
   - 单一来源可伪造，多独立来源一致才可信（AegisFlow 4 系统 / Signet 七重检查）
   - 决策是"计算"出来的不是"写死"的（规则读字段不读文件名）
   - 权重调不动诚信门槛（integrity cap）

4. **诚实可追溯 = 信任的基础**
   - 公开账本 + LIVE/LOCAL/DEMO 标注（AegisFlow）
   - 证伪记录 DISPROVED，不掩盖错误（Chancery）
   - 查不到 = unknown 绝不 pass（Signet）
   - 操作证据而非隐藏模型推理（DealForge）

5. **可验证性 = 最强的说服力**
   - 纯函数决策引擎 + 证据包可离线重演（Chancery/Signet）
   - 大量自动化测试（35/817）
   - 最终演示到达"真实完成工件"而非模拟成功界面（DealForge）

### 对 CodeRisk + AWS 参赛的落地设计蓝图
1. **Agent 工具分级**：用"可逆/不可逆"定义工具权限，不可逆操作锁定给人类（AegisFlow agent-tools.ts）
2. **Agent C 升级"多源合议"**：引入多独立来源一致性判定，每项独立证据（Signet 七重检查）
3. **权威计算确定性**：Agent C 输出严重级/风险评分用代码算，LLM 只给理由（DealForge）
4. **证据可追溯落地**：每条 PITAX 结论强制绑定证据行+来源（Chancery grounded or absent）
5. **证伪记录机制**：Agent C 验证失败记录 DISPROVED，不默默忽略（Chancery CLAIMS.md）
6. **报告生成 vs 发布分离**：生成后需人类授权才发布/发送（DealForge Draft≠Send）

### 定位
> **"外科医生在每次切开前都会停下来确认。医美机构没有这个停顿。Time-Out 就是那些房间缺失的'术前暂停'——检查谁在注射、用什么、患者是否真正理解，证据不足就拒绝。"**

### 解决的痛点（具体 + 数据支撑）
- WHO 外科清单研究：并发症 11.0%→7.0%，住院死亡率 1.5%→0.8%（Haynes et al., NEJM 2009）
- 美国约 13,000 家医美机构，增速快过监管；拿针者可能是美容师/"激光技师"/护士（在没人见过的委托协议下）
- 医美事故主因不是手不稳：缺少知情同意、风险沟通失败、对委托人的责任——全是文书失败，且都可在扎针前判定
- 2026 年 4 月 FDA 警告德州医美机构：买的正品 Botox 与记录注射对不上

### 核心机制
**七项检查（德州规则 + 实际存档证据）**
1. 执照有效、本州、未过期？
2. 此人获准做这个吗（直接或文档委托）？—— 职位头衔本身永远不是答案
3. 有患者专属医嘱、签署方案、当前 BLS、可用主管吗？
4. 术前评估记录了吗？
5. 产品批次捕获且无确认警报？
6. 患者通过"复述"测试吗（用自己的话说出风险，而非打勾）？
7. 有任何纪律处分吗？

**三种答案：CLEAR / BLOCKED / REVIEW**。规则模糊时软件明说并让有名有姓的人类决定，从不猜。

### 关键设计
1. **阻断得好 = 整个产品（Blocking well is the whole product）**
   - BLOCKED 不是错误消息——明确指出缺失文档、引用德州规则、告诉诊所怎么修
   - 补证据重跑，没人编辑数据库（"阻止你的软件"vs"帮助你的软件"的分界）

2. **黄金法则**：软件从不定什么是合法的，没有模型做算术。模型读文档成带置信度的类型化字段，判定来自对引用规则表的确定性代码，任何不确定停给有名有姓的人。

3. **出报告后仍可逆**：FDA 警告信在受理就绪后到达 → 返回审核。Ready 是可逆的。

4. **追加日志 + 记名**：每次尝试进只追加日志记下尝试者，没有东西被悄悄编辑。

5. **患者安全收据**：检查了什么/谁负责/皮肤基线/规则集指纹 → 发布 DNS 供验证，无需信任我们。

6. **Agent + 人类签名分工**：Agent 组装记录后停止，Medical Director 通过 eSign 亲手签署。

7. **完整 API**：七项检查一次 HTTP 调用，无注册无 key；展示所有可能的拒绝方式 + 真实状态，真实数据存储前拒收。

### 技术栈
Xano（17 表/13 端点/8 函数/状态机+守卫/审计日志/静态站）+ Nutrient DWS（文档→类型化字段+置信度+坐标）+ SerpApi（实时搜 FDA 警告信+德州委员会行动）+ Doctavian + Foxit eSign + Next.js/React

### 💡 对 CodeRisk 可借鉴点
| Time-Out 做法 | CodeRisk 可借鉴 |
|--------------|----------------|
| 软件不定合法性，模型不做算术 | Agent 判定来自确定性规则代码，LLM 只读文档给置信 |

# 应用型获奖项目速览（非核心赛道，赢在创意落地）

> 以下 6 个项目不属于"AI Agent 安全 + 人类责任"核心赛道，但各自有值得借鉴的落地设计。

## 1. PantryProof（食物召回证据追溯）
- 核心问题：食物银行如何证明"每个伙伴都完成了正确的召回响应，且不让不确定的 AI 预测做最终安全决定"
- 设计：把碎片化召回通知/库存/捐赠/响应动作转成"证据链 + 可重放的完结包"（replayable closure packet）
- **可借鉴：** "AI 预测不做最终安全决定"+"证据链可重放"——与核心赛道的可验证性一脉相承

## 2. AccessForm（AI 语音填表）
- 核心设计：语音描述 → 找到官方真实表格 → 逐题用平实语言询问 → 填真实 PDF → 短信告知缺什么
- **铁律：永不代替提交、永不签字、永不定资格**；无法验证官方表格就停下明说
- **可借鉴：** "AI 代办但守住边界（不提交/不签字/不裁定）"——精简版的权限边界设计

## 3. DepositCheck（押金诈骗防范，SerpApi 1st Place）
- 核心设计：租房押金转账前，上传房源照片 → Google Lens 反向搜图 → 找出这张图曾出现在哪 → 指出"真正的主人"地址
- **可借鉴：** 反图搜索做"多源交叉验证"（照片真实性）——防诈骗的轻量多源验证

## 4. compare.ai（Chrome 购物 AI 时尚顾问）
- 核心设计：浏览器内常驻的 AI 时尚顾问，逐产品分析，用虚拟试穿生成"穿在你身上"的图
- **可借鉴：** 产品级"personalized 决策"体验（把"模特上身"换成"我上身"）

## 5. LaunchKit（域名 + 品牌保护）
- 核心设计：一个域名替代 Bitly/Linktree/Gmail，AI 生成品牌名 + 品牌安全扫描（25 变体）+ DNS 管理
- **可借鉴：** "品牌安全扫描（brand safety scan）"思路——检测相似/仿冒域名，与 CodeRisk 的仿冒检测相关

## 6. Unmet（差评缺口分析）
- 核心设计：9 个 SerpApi 引擎做差评缺口排名——用户在求什么、什么坏了、Google AI 答案有没有引用你
- **可借鉴：** 多引擎聚合做"缺口洞察"——数据聚合方法论

---

## 对 CodeRisk 的落地启示（应用层）
- 这 6 个项目的共性：**都是"AI 帮人做事" + 守住一条明确边界**（不代提交、不签字、不裁定、不猜）
- 侧面印证了核心结论：**AI 应用获胜的关键不是"AI 多能干"，而是"AI 在多大范围内被信任地使用"**——边界设计比能力本身更打动评委
- 若 CodeRisk 做 Demo：可借鉴 AccessForm 的"AI 代办 + 守住边界"话术，或 DepositCheck 的"多源验证防诈"演示

# 获奖项目全景总结（14 个全览）

**已深挖核心方法论（5 个）：** AegisFlow / Chancery / Signet / DealForge / Time-Out
**已速览应用型（6 个）：** PantryProof / AccessForm / DepositCheck / compare.ai / LaunchKit / Unmet
**已抓详情未深挖（2 个）：** VOWS&VIBE（AI 试穿）/ 未抓到详情（DomainTwin AI / Nerve / DealProof）

**核心结论（指导 AWS 参赛）：**
> 真正的 AI Agent 安全 = 不可逆操作锁定 + 多源交叉验证 + 权威确定性分层 + 诚实可追溯 + 可验证性。CodeRisk 的 4-Agent 重构应把这些方法论落地为可测试的工程机制，而不是停留在 prompt 约束。
