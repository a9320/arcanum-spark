# 报告口径 · 误报处置 · 修复模板

## 1. 报告三件套（scripts/pitax_scan.sh --all 产出）

| 格式 | 用途 | 备注 |
|---|---|---|
| `.json` | 程序消费 / 回归比对 | `{summary, findings[]}`；summary 含 files_scanned/skipped、PITAX 版本 |
| `.sarif` | GitHub Code Scanning / IDE 插件 | SARIF 2.1.0；rules[] 携带 PITAX 元数据（ATLAS/CVE/参考链接） |
| `.md` | 人读交付 | 按 severity 分组，含证据/解码载荷/处置建议/参考 |

单格式：`--format JSON | SARIF | MD`；级别过滤：`--min-severity high`。
**生成 ≠ 发布**：报告只写本地目录；是否公开（提 issue / PR / 扫描平台上传）由用户决定，Agent 不得擅自外发。

## 2. 报告写作口径（不可妥协）

- 每条结论必须引用命中自带的位置/证据/编号；**禁止**编造编号、CWE、CVE 或"推测的"额外漏洞；
- **severity 只升不降**：规则层给的下限是底线，语义层复核可升级（附证据），不可降级；
- 零命中表述固定为两句：① 确定性规则未检出已知模式；② 空检出 ≠ 安全，未覆盖语义层与运行时层；
- 引用仓库内容入报告时脱敏（密钥类证据截断/掩码），对话中不贴明文 token。

## 3. 误报处置流程

1. 核对 `references/rules.md` 对应规则的"误报边界"（测试夹具 / 安全教材 / RTL 文案 / BOM）；
2. 读原文件确认上下文：是**发出指令**（恶意）还是**谈论攻击**（教材/夹具）；
3. 确认误报 → 在报告中标注"误报+理由"，不删除引擎原始输出（可审计）；
4. 当前引擎无内联豁免语法（确定性层故意不提供"一键忽略"，豁免只影响报告层，不抹除证据）；
   需要 CI 长期豁免时在报告目录维护 `exemptions.md`（文件+规则+理由+审批人），比对时过滤；
5. 拿不准 → 按真阳性报出并标注"待人工确认"，宁误报不漏报。

## 4. 修复建议模板（按规则族）

**通用结构**：做什么（移除/改写）→ 查来源（git blame / 提交者 /引入时间）→ 断传播（下游影响）→ 防复发（CI/审查门禁）。

- **T-46（AI 配置后门）**：删除命中行 → `git log -p <file>` 全量 diff 审查该文件 → 该仓库视为已投毒，盘点近 90 天指令文件变更 → 通知所有 clone 使用方；AI 配置文件加 CODEOWNERS 强制双人审查。
- **T-51 / N-06（注释/文档注入）**：删除或改写为中性描述（谈论攻击 ≠ 发出指令）；安全教材类可移入明确标注的 fixture 目录；对 AI 生成代码的注释保持抽检。
- **E-23 / E-54（字符层）**：批量清理不可见/Bidi 控制符（脚本化修复后重跑本扫描验证归零）；CI 增加 Unicode 白名单门禁；跨平台文档标注文本方向。
- **E-07/14/36/57（编码载荷）**：解码复核（`decode.py`）→ 确认恶意的直接删除；合法编码数据需求改明文 + 密钥管理；必须保留时在代码注释与报告中双重说明解码语义。

## 5. 与动态/语义层的分工

本技能 = 确定性第一道闸（毫秒级、零 token、结果可复现）。它不覆盖：
语义改写后的注入（换措辞的英文指令）、运行时行为、依赖供应链（SBOM）、传统漏洞。
完整审计 = 确定性层（本技能）+ Agent 语义层研判 + （可选）管线动态复核。报告中应如实标注覆盖范围。
